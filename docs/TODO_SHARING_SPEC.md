# Technical Specification: Todo Sharing

**Status:** Proposed for product and security review

**Version:** 1.0

**Owner:** Product Engineering

**Decision required:** Confirm todo-level sharing for v1. List/workspace sharing is intentionally deferred.

## 1. Product Context

### Problem

Todos are private to their owner. Users need a controlled way to let another
registered user read or update a specific todo without exposing the owner's
other todos or allowing the collaborator to manage access.

### Goal

Introduce explicit viewer and editor permissions for individual todos. The owner
can grant, inspect, change, and revoke access. Revocation must take effect on the
next authorization check and must remove stale shared-list cache entries.

### Non-goals

- Public or anonymous share links.
- Email invitations or notification delivery.
- Sharing an entire workspace or list in v1.
- Real-time collaboration, comments, attachments, or audit history UI.

## 2. Roles and Permission Model

| Role | Read todo | Update title/description/completed | Delete todo | Manage shares |
|---|---:|---:|---:|---:|
| Owner | Yes | Yes | Yes | Yes |
| Editor | Yes | Yes | No | No |
| Viewer | Yes | No | No | No |

The owner is implicit from `todos.user_id` and does not require a row in
`todo_shares`. A share is active while its row exists. There is no soft-deleted
share state in v1.

## 3. User Stories and Acceptance Criteria

### US-01: Grant viewer access

**As an** owner, **I want to** share one todo with an existing user as a viewer,
**so that** the user can read it without changing it.

Acceptance criteria:

- `POST /api/v1/todos/{todo_id}/shares` accepts a registered user's email and `viewer` role.
- A successful request returns `201 Created` and the new share identifier.
- The grantee can retrieve the todo through the shared-todo surface.
- The grantee cannot update, delete, or manage shares for that todo.
- The owner continues to see the todo in the owned list only once.

### US-02: Grant editor access

**As an** owner, **I want to** grant editor access,
**so that** a collaborator can maintain the todo's content and completion state.

Acceptance criteria:

- Editors can update only `title`, `description`, and `completed`.
- Editors cannot delete the todo or grant/revoke access.
- The update is committed atomically and refreshes `updated_at`.
- The owner's and grantee's affected caches are invalidated after commit.

### US-03: Review and change access

**As an** owner, **I want to** list current shares and change a role,
**so that** access remains auditable and adjustable.

Acceptance criteria:

- Only the owner can list or modify shares for a todo.
- A role change supports `viewer <-> editor` and returns `200 OK`.
- A duplicate share is rejected with `409 Conflict`; it does not create a second row.

### US-04: Revoke access

**As an** owner, **I want to** revoke access,
**so that** the grantee loses access immediately.

Acceptance criteria:

- `DELETE` returns `204 No Content` for an active share.
- The next read or update by the former grantee returns `404` or `403` without data.
- Shared-list and todo-detail cache entries for the grantee are invalidated.
- A request racing with revocation must re-check authorization before commit.

## 4. Domain and Data Model

### Existing tables

- `users(id UUID PRIMARY KEY, email, ...)`
- `todos(id UUID PRIMARY KEY, user_id UUID NOT NULL, ...)`

### New table: `todo_shares`

| Column | Type | Constraints and purpose |
|---|---|---|
| `id` | UUID | Primary key; generated by the application or database |
| `todo_id` | UUID | Not null; FK to `todos.id` with `ON DELETE CASCADE` |
| `owner_user_id` | UUID | Not null; FK to `users.id` with `ON DELETE CASCADE`; must match `todos.user_id` |
| `grantee_user_id` | UUID | Not null; FK to `users.id` with `ON DELETE CASCADE` |
| `role` | VARCHAR(20) | Not null; check constraint limited to `viewer` or `editor` |
| `created_at` | TIMESTAMPTZ | Not null; default `now()` |
| `updated_at` | TIMESTAMPTZ | Not null; default `now()` and refreshed on role change |

Constraints:

- `UNIQUE (todo_id, grantee_user_id)` prevents duplicate active shares.
- `CHECK (owner_user_id <> grantee_user_id)` prevents self-sharing.
- A database trigger or service-level invariant must ensure
  `owner_user_id = todos.user_id`; the API must never trust a caller-provided owner ID.
- Deleting a todo or either participating user cascades to share rows.

Indexes:

```sql
CREATE INDEX ix_todo_shares_todo_id
    ON todo_shares (todo_id);

CREATE INDEX ix_todo_shares_grantee_todo_id
    ON todo_shares (grantee_user_id, todo_id);

CREATE INDEX ix_todo_shares_owner_todo_id
    ON todo_shares (owner_user_id, todo_id);
```

The grantee composite index supports the shared-list join and authorization
lookup. The owner composite index supports share management screens.

## 5. API Contract

Base path: `/api/v1`. All endpoints require `Authorization: Bearer <access-token>`.

| Method | Endpoint | Caller | Purpose | Success |
|---|---|---|---|---|
| POST | `/todos/{todo_id}/shares` | Owner | Create a share | `201 Created` |
| GET | `/todos/{todo_id}/shares` | Owner | List active shares | `200 OK` |
| PATCH | `/todos/{todo_id}/shares/{share_id}` | Owner | Change role | `200 OK` |
| DELETE | `/todos/{todo_id}/shares/{share_id}` | Owner | Revoke share | `204 No Content` |
| GET | `/todos/shared` | Grantee | List todos shared with caller | `200 OK` |
| GET | `/todos/{todo_id}` | Owner or active grantee | Read one todo | `200 OK` |
| PUT | `/todos/{todo_id}` | Owner or editor | Update permitted fields | `200 OK` |

### Create share

Request:

```json
{
  "grantee_email": "collaborator@example.com",
  "role": "viewer"
}
```

Validation:

- Email must be normalized using the same policy as login/registration.
- `role` must be exactly `viewer` or `editor`.
- The target user must already exist in v1.

Response:

```json
{
  "id": "share-uuid",
  "todo_id": "todo-uuid",
  "grantee_user_id": "user-uuid",
  "grantee_email": "collaborator@example.com",
  "role": "viewer",
  "created_at": "2026-10-06T12:00:00Z",
  "updated_at": "2026-10-06T12:00:00Z"
}
```

### Change role

Request:

```json
{
  "role": "editor"
}
```

The owner is resolved from the authenticated token and the todo row. The client
cannot choose `owner_user_id`, `grantee_user_id`, or `todo_id` in the payload.

### Shared list

`GET /todos/shared?page=1&size=20` returns only todos for which an active share
exists for the authenticated user. Results are ordered by
`created_at DESC, id DESC`, matching the owned-list contract. Each item includes
the effective role so the UI can disable editor-only actions.

### Error format and status codes

All errors use the existing FastAPI shape:

```json
{
  "detail": "Human-readable message"
}
```

| Status | Meaning |
|---|---|
| `401` | Missing, expired, malformed, or wrong-class access token |
| `403` | Authenticated user lacks the required owner/editor permission |
| `404` | Todo, share, or shared todo is not visible to the caller |
| `409` | Duplicate share or conflicting role operation |
| `422` | Request validation failure |

For unknown grantee emails, return a generic message such as
`Unable to share with this user` to reduce account enumeration. Product may
choose `404` or `400`, but the choice must be consistent.

## 6. Authorization and Transaction Rules

1. Resolve the caller from a verified access token.
2. Load the todo and its owner identity in the same database transaction.
3. For owner operations, require `todos.user_id = current_user.id`.
4. For grantee read/update operations, load the matching share by
   `(todo_id, grantee_user_id)` and enforce its role.
5. For editor updates, lock or re-check the share row before commit so a revoke
   cannot be bypassed by a request that started earlier.
6. Commit the database mutation before invalidating Redis keys. If the database
   transaction rolls back, no cache invalidation should advertise a state that
   was never committed.

### Concurrency behavior

- Duplicate creation relies on the unique constraint; map the database conflict
  to `409` rather than performing an unsafe check-then-insert only.
- Concurrent role changes are last-write-wins, with `updated_at` available for
  optimistic concurrency in a later version.
- Revoke wins over an in-flight editor request when the final authorization
  check occurs before commit.
- Deletion of a user or todo cascades shares and invalidates affected list keys.

## 7. Cache Design

| Data | Key pattern |
|---|---|
| Owned list | `todos:user:{owner_id}:page:{page}:size:{size}` |
| Shared list | `todos:shared:user:{grantee_id}:page:{page}:size:{size}` |
| Per-user detail (optional) | `todo:{todo_id}:user:{viewer_id}` |

Required invalidation:

- Todo create/update/delete: owner list, todo detail keys, and shared-list keys
  for all active grantees.
- Share create/update/revoke: grantee shared-list keys plus detail keys for the
  todo for both owner and grantee.
- Use Redis `SCAN` with a bounded prefix rather than `KEYS`.
- TTL remains five minutes, but authorization must be checked at the origin for
  every uncached request. Never use a cache key that omits the viewer identity.

## 8. Observability and Audit Signals

Every share mutation should emit structured logs with:

- `actor_user_id`
- `todo_id`
- `grantee_user_id`
- `share_id`
- `old_role` and `new_role` where applicable
- result (`created`, `updated`, `revoked`, `rejected`)
- request correlation ID and duration

Do not log access tokens, passwords, or full todo content. A durable audit table
is deferred from v1 but should consume the same event fields if introduced.

## 9. Rollout and Migration Plan

1. Add the table, constraints, and indexes in an additive migration.
2. Deploy authorization code that treats the absence of a share as private access.
3. Backfill no rows; existing todos remain owner-only.
4. Enable the owner share-management API behind a feature flag if staged rollout
   is required.
5. Monitor `403`, `404`, duplicate-conflict, and cache-invalidation metrics.
6. Remove the feature flag after security and cache correctness metrics stabilize.

For large production tables, create indexes concurrently in a migration mode
that does not run inside a transaction, or schedule a maintenance window.

## 10. Acceptance Test Scenarios

- Owner creates viewer share; viewer reads; viewer update/delete returns `403`.
- Owner creates editor share; editor updates title and completion; delete returns `403`.
- Owner changes viewer to editor and back; effective permission changes immediately.
- Owner revokes access; grantee cannot read from API or stale browser cache.
- User cannot share a todo with themselves.
- Duplicate share returns `409` and leaves one row.
- Non-owner cannot list, change, or revoke shares.
- Deleting todo or user removes share rows through cascade behavior.
- Shared list never includes an unshared or owner-only todo.
